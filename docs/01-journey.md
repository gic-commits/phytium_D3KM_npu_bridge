# 从零到跑通：飞腾 D3000M NPU 的完整历程

> 这篇文档的价值不在"结论"，而在**被推翻的假设**。我们在这块 NPU 上前后花了几十轮，
> 其中**大多数时间用来否掉看起来非常合理的猜想**。按顺序读完，你能省掉这些弯路。

## 0. 起点：什么都没有

| 现状 | 事实 |
|---|---|
| 硬件 | 长城 N90F3 笔记本，飞腾 D3000M。`ACPI PHYT0050` 状态 = 15（设备在位） |
| 内核 | 麒麟 V10 SP1，5.4.18-168，aarch64。**没有** `CONFIG_VHA`，也没有任何 NPU 相关驱动 |
| 用户态 | 厂商提供闭源运行时 `npu-ftn300-rt-lib-kylinv10`（2 月版）。`strings` 显示它只认 **`/dev/phy_npu%d`** |
| 模型 | 厂商给了编译好的模型包（`.json` + `.params` + `.so` + `.tar` 容器，magic `42efbe42`） |
| 能不能跑 | **不能**：没有驱动 → 没有设备节点 → 库连不上 |

**第一个决定性选择**：厂商的 VHA 内核驱动拿不到 ⇒ 改用 **deepin 开源驱动**
`drivers/staging/phytium-npu`（同血统、但 uapi 与厂商库**不一致**），自己写一层
**VHA 兼容桥接**把两边对上。这就是本项目的技术主线。

> 教训一：**先确认"官方是否开源了一版"**。同 IP 的开源驱动哪怕 uapi 不同，也远胜从零逆向硬件。
> 本项目移植后 `probe` 一次就命中了 `PHYT0050`。

## 1. 认识对端：抓出 VHA 的 ioctl 真值（第 1–3 轮）

- 用 `strace -f -y` 抓库的系统调用序列，`cmd = dir<<30 | size<<16 | type<<8 | nr` 解码，
  得到 VHA 命令表（`type = 0x71`，即字符 `'q'`），逐条映射到驱动等价操作。
- 结构体大小与官方头 `sizeof` **逐一对齐**后可直接 `memcpy`（16 / 80 / 536 字节三个结构体完全吻合）。
- 寄存器表：**平台/ACPI 变体走 `leopard`（基址 0x10800）**，PCI 变体才是 0x10000。
  判法：`grep -n '#include.*reg\.h' *_platform.c` 看它实际 include 哪份。
- 启动序列缺一不可：
  `clock → hl_wdt → mmu_config_dev_mmu → config_dma_address → clear_event → config_event(ALL,1) → start`
- `CONTROL` 编码：`ctrl = min(2048, stream_size); ctrl = (ctrl/32 - 1) << 1; ctrl |= START_EN(0x1)`。
  ⚠️ **`stream_size == 0` 时该表达式在 u32 下溢成 `0xFFFFFFFF`** ⇒ 引擎不取指且无任何报错。

## 2. 被推翻的假设（**省时重点**）

| # | 看起来非常合理的假设 | 实测结论 | 怎么被推翻的 |
|---|---|---|---|
| 1 | `page37`(39592B) 是命令流缓冲，需要内核从文件装载 | **假**。真正的命令流缓冲是 `CMDS(page95, 25536B)`，内容 = 模型容器 `MBS[676:]` 的切片 | `crc32(page95 前 25536B) == crc32(MBS[676:26212]) == 0xa92e4a5d`，而 `MBS[0:25536]` 不符 |
| 2 | "只读 mmap + 内容全 0" ⇒ 内核没装载 | **弱启发式，害人**。那只说明"库不打算让 host 读它" | 库对 host 要读的缓冲都会主动 mmap；命令流早已由库写好 |
| 3 | 引擎没动是因为"流太大 / 缓冲地址太高 / 核数不够 / 包代别不匹配" | **全假**。ResNet50 的命令流更大、缓冲地址更高，10/10 正常 | 用"比它更极端却能跑通"的样本一击排除 |
| 4 | "取指字数打满 = 执行完成" | **假**。那只证明预取/取指通路活着 | 输出缓冲前后 CRC + 同一输入跑两遍才证明真执行 |
| 5 | "没有完成事件" ⇒ 事件没触发 | **假**。是内核 IRQ top-half **先读到并清掉了**事件，桥接的轮询永远读到 0 | 加了 IRQ 日志后发现事件每次都来 |
| 6 | "输出写不回来是硬件/时序问题" | **假**。根因是桥接把输出缓冲**映射成了只读**（见 `docs/03`） | 全 buffer 前后 CRC 扫描 + `ADDR_USED` 逐位复算 |
| 7 | "引擎写了输出，app 就该看到" | **假**。厂商运行时**图尾的拷贝节点没执行**，`out_mats[i]` 恰好全 0 | 同进程页级直读工具 `npu_peek` 对比 |
| 8 | 同进程第二次推理慢 40 s 是"硬件慢/硬件等" | **假**。是**我们自己的看门狗把「循环次数」当成「毫秒」**（本内核 `msleep(1) ≈ 8 ms`） | 模块自报耗时 vs dmesg 墙上时间戳不一致 |
| 9 | 完成判定可以看"输出 CRC 变了" | **原理性错误**。输入相同 ⇒ 结果相同 ⇒ CRC 恒定不变 | 第 2 次起恒定超时的现象暴露了它 |
| 10 | 多模型挂死是"引擎/桥接问题" | **假**。是厂商库**按响应里的 `sid` 匹配任务**，而同进程内各图的 `sid` 相同 | 见 `docs/04`：strace + gdb + LD_PRELOAD 三件套定位 |
| 11 | "切模型时销毁旧引擎"就能支持多模型 | **假**（实测证伪）。映射活在**进程级** | 服务日志出现"淘汰模型"后依旧挂死 |

**方法总结**：本项目 60% 的时间花在"用一个便宜实验否掉一个贵猜想"。
每轮只做一件事、留可复现证据（dmesg / 寄存器读数 / CRC / 反汇编），
并把"结论"和"未验证假设"分开写——**我们曾两次把桥接自己的 bug 写成"硬件限制"**。

## 3. 桥接修好的 6 处缺陷（第 9–29 轮，详见 `docs/03`）

1. `map_type` 用**未初始化**的 `req.flags` 计算 ⇒ 输出被映射成只读 ⇒ **间歇性写回失败（~40%）**。
   症状：IRQ 每次都来、硬件计数完全一致、就是有时写不回来。
2. 完成判定里 `if (!mapped || size > 65536) continue;` 白名单 ⇒ **输出 >64 KB 的模型**
   （yolov5s/scrfd）完成位永不置位 ⇒ 对端库挂死。而小模型（yunet）一直"正常"，把 bug 藏了好几轮。
3. 看门狗 `for (t; t<5000; t++) msleep(1)` —— **把循环次数当毫秒**，本内核 `msleep(1)≈8 ms`
   ⇒ 每次空转 ~40 s。改用 `ktime` 真实截止后 **40.6 s → 5.0 s**。
4. 完成判定用"输出 CRC 变化" ⇒ 同输入结果恒定 ⇒ 必然漏判。改用 **IRQ 响应 + 累计计数**
   （`vha_rsp_served++`，读响应路径原子自增）⇒ **5.0 s → 0.42 s**（相对最初 **97×**）。
   ⚠️ 判断异步完成**一律用累计/单调量**，绝不用"列表瞬时长度"（会被并发消费者吃掉）。
5. 厂商库交付缺陷（**图尾拷贝节点不执行**）的补齐：内核侧 `vha_int_fixup` 只能用于联调取证
   （触发点必须在"用户态 mmap 该缓冲"的时刻；不能拿"只增不删"的表当判据），
   **正确落点是用户态 compat 层**（见下）。
6. 官方 `if (!fd[i]) continue;` 把"句柄 0"当空槽 ⇒ 会**静默漏掉输入缓冲**（本库输入句柄恰好是 0）。

## 4. 交付层：引擎算了，App 看不到（第 15–29 轮）

现象：**输出缓冲 CRC 变了**（引擎确实写了），但 App 的 `out_mats[i]` **恰好全 0**。

排查结论（三段）：
1. `out_mats[i]` 是**库自己 malloc 的 host 缓冲**，不是设备页映射 —— 用 `/proc/self/maps` 反查即可证；
2. 厂商运行时**本该在"拷进 dnn_buf_"这一步做 2 类 softmax（容器里 `softmax@213`），却整步跳过**；
   同时**图尾 `__copy` 节点没执行** ⇒ 设备页 → App Mat 的搬运缺失；
3. ⇒ **正确落点 = 用户态 compat 层**：`execute_graph` 返回后，直接读引擎那一页、施加激活、
   **写进 `out_mats[i].data`**。零内核改动、App 零改动，实测把 `out[1]` 从恒 0 变成真概率，
   解码结果与人脸金标 `IoU = 0.939`。

内核侧同类修补（`vha_int_fixup`）之所以"也能生效"，是因为它**赶在库那次拷贝之前**；
但内核做不成接口（寄存器/启发性配对/内核禁浮点），所以只作为联调取证手段保留，默认关闭。

## 5. 服务化：多模型为什么必须多进程（第 30 轮）

- 现象：服务里跑第 2 个模型（不同图）**必挂**；同一模型连跑 13 次全绿。
- 定位（三件套）：`strace -f` 看到响应在提交线程还阻塞于 `write()` 时就被库的响应线程读走；
  `gdb thread apply all bt` 看到卡在 `VhaNotifyImp::WaitForCompletion`；
  **LD_PRELOAD 探针**抓到两次请求的响应**字节完全相同**（`sid` 都是 `0x10101`）。
- 结论：库**按 `npu_user_rsp.sid` 匹配任务**，而同进程内不同图的 `sid` 相同 ⇒
  第 2 条响应被投递给**第 1 个图残留的任务对象** ⇒ 新任务永远等不到。
- 修复路径：先试"切模型时销毁旧引擎"⇒ **实测无效**（映射活在进程级）⇒
  **定案：隔离边界 = 进程**，即 supervisor + 每模型一个 worker 子进程（见 `docs/05`）。

## 6. 现在的状态

- 5 模型端到端全绿、`oops=0`；服务化（进程池）已跑通"原来必挂序列"；
- 已实现 `npuworker` / `npusvc_pool` / 客户端库里 `npu_infer_ex`（张量级，含 1D 语音特征）与
  `npu_detect_yunet`（图像级薄封装）、systemd unit、冒烟自检脚本；
- 待办：**并发（两客户端同时）用例**曾失败（`NPU_E_SOCKET`，现场为 worker `init_graph` 后挂住，
  dmesg 无崩溃）——判定性复现步骤见 `docs/05` §五；worker 超时击杀路径需用极小阈值做确定性验证。
