# 架构与数据流

## 一、分层

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 应用 / 客户端                                                            │
│   npu_cli（示例）  libnpuclient.a（张量级 npu_infer_ex / 图像级 detect）  │
│   或：厂商 phyAIEngine API（init_graph / execute_graph）—— 二者都支持     │
└───────────────┬──────────────────────────────────────────────────────────┘
                │  unix socket，帧协议 NPU1（首行 + 文本头 k=v\n + 二进制载荷）
┌───────────────▼──────────────────────────────────────────────────────────┐
│ npusvc_pool —— supervisor（不碰设备、不建图）                             │
│   优先级队列(0/1/2, 同 FIFO) · 队列超时 · **worker 超时击杀** · 空闲回收   │
│   同一时刻只存活一个 worker；切模型 = 回收旧 + 拉起新                      │
└───────────────┬──────────────────────────────────────────────────────────┘
                │  管道（同帧协议，走高位 fd）
┌───────────────▼──────────────────────────────────────────────────────────┐
│ npuworker —— 执行体（**一个模型一个进程**）                                │
│   独占 /dev/npu0 · 厂商库 phyAIEngine · 元数据后处理（读引擎页→激活→写 Mat）│
└───────────────┬──────────────────────────────────────────────────────────┘
                │  ioctl / write（VHA 接口，type='q'=0x71）
┌───────────────▼──────────────────────────────────────────────────────────┐
│ 内核：开源驱动 phytium-npu（deepin staging）+ **我们的 VHA 兼容桥接**       │
│   src/phytium_npu_uapi.c  ← 本项目改动集中在这一个文件                     │
│   · VHA 命令 → 驱动等价操作（属性/分配/映射/SET_BUF/SYNC_BUF/提交）        │
│   · 提交描述符解析 → leopard 寄存器编程（CMD_BASE/ADDR*/CONTROL/EVENT）    │
│   · 完成判定/看门狗 · 审计与取证打点（[VHA-*] 日志）                       │
└───────────────┬──────────────────────────────────────────────────────────┘
                ▼
        硬件：飞腾 D3000M 内置 NPU（寄存器基址 0x26d00000 物理 / leopard 视图 0x10800）
```

**为什么"厂商库"和"我们的客户端"都能用**：桥接之后 `/dev/npu0` 对厂商库而言就是它认识的 VHA 设备，
所以厂商的 `phyAIEngine` API **可以直接用**（这也是我们最初验证推理链的方式）；
`libnpuclient` 只是把同一能力包成更稳定的服务接口，便于多应用共享。

## 二、关键设计取舍

| 决策 | 选择 | 原因 |
|---|---|---|
| 驱动来源 | 开源 deepin 驱动 + 自写 VHA 桥接 | 厂商 VHA 内核驱动拿不到；同 IP 开源实现胜于从零逆向硬件 |
| 桥接位置 | **内核态**（驱动 ioctl `switch` 加 case） | 库的每一次提交/映射都必须落到真实硬件；用户态无 mknod/dma 能力 |
| 交付缺陷修补 | **用户态 compat 层** | App 的输出 Mat 是**库自己 malloc 的 host 缓冲**，只有"持有该 Mat 的进程"能写进去；内核侧只能做联调取证 |
| 多模型服务化 | **每模型一进程**（进程池） | 厂商库**不支持同进程多图**（响应按 `sid` 匹配，各图 `sid` 相同 ⇒ 撞车），且设备单实例 |
| 传输协议 | unix socket + 文本头 + 二进制载荷 | 零依赖、零权限、易调试（`cat` 就能看头）；张量级接口天然支持任意 ndim（含语音 1D） |
| 队列策略 | 单工作线程 + 优先级队列 | NPU 单实例，串行是物理约束；优先级保证交互式请求不被批任务饿死 |

## 三、数据流（一次推理）

1. 客户端组帧：`SHAPE=1,3,112,112`、`DTYPE=f32`、`PRIO` 与 fp32 载荷（或图像级：客户端做预处理）
2. supervisor 入队（按优先级）→ 取模型：与当前 worker 同模型 ⇒ 直接转发；否则**回收旧 worker、拉起新 worker**
3. worker：`eng->execute_graph(ins, outs)` → 厂商库走 VHA ioctl → 桥接编程寄存器 → 引擎执行 → IRQ 完成 → 库返回
4. worker 做**元数据后处理**：按 `<模型>.meta.txt` 里声明的 `<输出下标> <引擎页号> <op>`，
   读引擎写的那一页 → 施加 `softmax2`/`sigmoid`/`none` → 写进 `out_mats[i].data`
   （**补的正是厂商运行时漏掉的那一步**）
5. worker 把 `COUNT/BYTESi/SHAPEi` + 载荷回给 supervisor → 原样透传给客户端

## 四、模型侧的元数据（`<模型名>.meta.txt`）

```
# <输出下标> <引擎写该输出的设备页号> <op:none|softmax2|sigmoid>
1 93 softmax2      # yunet: 第 1 个输出在设备页 93，需要 2 类 softmax
```
- **页号从哪来**：桥接的 `[VHA-ALLOC] page=… size=…` + 缓冲名字（`INT-3`/`CMDS-8`/`dnn_buf_`…）
  与实际输出尺寸交叉确认；换模型/换工具链后**页号会变**，需重新探一次。
- **为什么要声明激活**：库交出来的是**pre-softmax logits**（见 `docs/06`），不施加 softmax
  会得到"框对、分数错、误检 13 个"。

## 五、代码地图

| 路径 | 角色 |
|---|---|
| `src/phytium_npu_uapi.c` | **本项目内核侧全部改动**（VHA 桥接 + 完成判定 + 打点） |
| `svc/npuworker.cpp` | 执行体：独占设备、单模型、后处理 |
| `svc/npusvc_pool.cpp` | supervisor（进程池版，**推荐**） |
| `svc/npusvc.cpp` | 单进程版服务（历史版本，保留用于 A/B 对照与回退） |
| `svc/npuclient.{h,cpp}` | 客户端库：`npu_infer_ex`（张量级）/ `npu_detect_yunet`（图像级） |
| `svc/npu_cli.cpp` | 示例客户端：`infer` / `face` / `bench` / `status` |
| `svc/npuworker`+`npusvc_pool` | 编译产物（需自备厂商头/库，见 `docs/08`） |
| `tools/npu_det.cpp` | 最小运行器：直接调厂商 `phyAIEngine`，多模型/多输入尺寸/多归一化口径 |
| `tools/npu_peek.cpp` | **同进程内按页号读设备缓冲**（破案关键工具；跨进程必 `ENODEV`） |
| `tools/regsnap.py` | 48 个关键寄存器一次性快照（只读 `/dev/mem`） |
| `scripts/*` | 取证：ELF 字符串/反汇编定位、MBS 容器解析、全 0 CRC 判"写过没" |
