# 桥接（内核侧）六处缺陷：定位方法、症状、修法

> 全部改动集中在 `src/phytium_npu_uapi.c`（相对 deepin 开源驱动）。
> **这 6 条里有 5 条是我们自己写桥接时引入的 bug，第 6 条是照抄官方写法踩的坑。**
> 它们全部伪装成"硬件问题"，平均每条花掉 1–3 轮。

---

## ① `map_type` 用未初始化的 `req.flags` ⇒ 输出被映射成只读（最贵的 bug）

**症状**：推理结果**间歇性写回失败（约 40%）**；IRQ 每次都来；硬件计数（取指、cache 请求、fence）**完全一致**；
失帧与正常帧的寄存器快照逐位相同；输出缓冲有时全 0。

**根因**：`copy_from_user(&req, ...)` **之前**就用 `req.flags` 算出了 `map_type`（读的是未初始化栈值）：

```c
case VHA_MAP_BUF: {
    u32 mtype = (req.flags & 0x4) ? NPU_MAP_TYPE_INFERENCE : NPU_MAP_TYPE_BUF;   // ← req 此时还未 copy！
    if (copy_from_user(&req, ...)) return -EFAULT;
```

`map_type` 的 0x4 位 = `NPU_MAP_TYPE_RO`，官方把它翻成 MMU 页属性 `flags = 0x2`（**只读**）：

```c
flags = ncmap->map_type & NPU_MAP_TYPE_RO ? 0x2 : 0;    /* 官方 mm_mu.c 同处 */
```

⇒ 输出缓冲被映射成**只读** ⇒ 引擎写不回去。而映射**合法**（MMU 无 fault）、取指照跑、计数照涨，
于是完美伪装成"硬件时好时坏"。

**修法**：把 `mtype` 计算移到 `copy_from_user` **之后**。修好后 **14/14 写回**，
`ADDR_USED` 从垃圾值回到 `0x20007e`（与库真实 flags 逐位吻合）。

**纪律**：
1. 桥接里每个参数结构体一律先 `memset`/`{}` 初始化；
2. **任何"先算后用"的字段必须移到 `copy_from_user` 之后**；
3. `-O2 -Wmaybe-uninitialized` 编一遍；
4. **凡"每次行为不同、而硬件计数完全相同"，第一嫌疑永远是自己代码里的未初始化值/UB**，不是硬件时序。

## ② `vha_out_crc()` 的尺寸白名单 ⇒ 完成位永不置位（大缓冲模型必挂）

**症状**：yolov5s / scrfd **"流取完、无 fault、不发完成事件"**：`CMDREQ_RD_WORD` 恰好等于命令流总字数
（如 `0x961` = 2401 字）、`MDBG_IDLE=0xffff`、`FAULT=0`，但对端库**挂死**。而 yunet（输出 ≤64 KB）一直正常。

**根因**：我们自己的完成判定里有：

```c
static u32 vha_out_crc(void) {
    list_for_each_entry(e, &vha_allocs, list) {
        if (!e->mapped || e->size > 65536) continue;    /* ★ 输出 >64KB 的模型：CRC 恒 0 */
        ...
```

⇒ 输出**全部** >64 KB 的模型（yolov5s 输出 8.5 MB、scrfd 类似）CRC 恒 0 ⇒ `done` 永不置位 ⇒
5 s 超时 ⇒ **不推完成响应** ⇒ 对端库挂死。这条 bug 因为"小模型一直正常"而藏了好几轮。

**修法**：完成判定**禁止按尺寸/页号/名字做白名单**——改成"排除输入页 + 全量纳入 + 大缓冲头尾采样"。

**纪律**：**自家窄探针与更宽的对照 dump 打架时（`done=0` 但 `[VHA-CRC-after]` 明明变了），先怀疑窄的那个。**

## ③ 看门狗把"循环次数"当"毫秒" ⇒ 每次空转 ~40 秒

**症状**：同进程**第 1 次推理 0.42 s、第 2 次起固定 40.6 s**。日志打的是 `after 5000ms`（其实是**循环计数**），
极易被误读成"硬件等了 40 秒"。

**根因**：

```c
for (tmo = 0; tmo < 5000; tmo++) { msleep(1); ... }   /* 本内核 msleep(1) 实际 ≈ 8 ms */
```

⇒ 5000 × 8 ms ≈ 40 s。**定位三招**（通用）：
1. 给候选段各加 `ktime` 打点 + 一个"跳过该段"的模块参数 ⇒ **一次重载排除一个假设**；
2. **模块自报耗时 vs dmesg 墙上时间戳不一致 ⇒ 问题在自己代码**（一致才是硬件在等）；
3. 用时间窗口在 dmesg 里找"静默段"（整段无日志）⇒ 时间耗在没打点的循环里。

**修法**：改用 `ktime_get_ns()` 真实截止 ⇒ 40.6 s → 5.0 s。

## ④ 完成判定用"输出 CRC 变化"与"响应列表长度" ⇒ 原理性漏判

**症状**：修好 ③ 后仍稳定 5 s 超时；`init_graph` 很快、首跑正常。

**根因（两条，都是判定口径错）**：
1. **"输出 CRC 变了才算完成"**——同一个输入重复推理，**结果逐轮相同 ⇒ CRC 恒定不变**，
   判据在原理上就不可能命中；
2. 改用"响应列表长度 > 之前"——**列表会被对端库的并发消费者吃掉**（先增后减），必然漏判。

**修法**：完成信号走 **IRQ 响应 + 累计量**：读响应路径 `copy_to_user` 之后 `atomic_inc(&vha_rsp_served)`，
判定只比较累计值是否增长；同时保留 `来源=IRQ响应/CRC/超时` 的日志便于取证。

```c
int served_before = atomic_read(&vha_rsp_served);
... 等待 ...
if (atomic_read(&vha_rsp_served) > served_before) { done = 1; src = 1; }   /* IRQ 响应 */
```

⇒ 5.0 s → **0.42 s**（相对最初 **97×**）。

**纪律**：**判断异步完成一律用累计/单调量**，绝不用"列表瞬时长度""状态位翻转"这类会被并发改变的量。

## ⑤ 交付补齐的触发点与判据（v1 完全失效，v2 才生效）

**背景**：厂商运行时漏了"设备页 → App Mat"的搬运（见 `docs/01` §4）。

**v1 的错**（两处，都是判据问题）：
1. 触发点放在**提交/完成路径**；而对端库是**完成之后才 mmap 输出缓冲** ⇒ 判据永不成立、静默空转；
2. 拿全局 `vha_mmaps`（**只增不删**，全文无 `list_del`）当"该页未映射"的判据 ⇒
   任何进程映射过一次就把判据**永久毒化**（实测：跑过一次页级读取工具后，同会话 3 次全不触发）。

**v2 的修法**：触发点搬到 **用户态 `mmap` 该缓冲的那一刻**；弃用 `vha_mmaps` 判据，
改为"同尺寸 + 引擎写过"的可门控启发式，并逐次打印
`[VHA-INTFIX] fill page=B <- page=A size=N`（可观测、可一键关闭 `echo 0 > .../vha_int_fixup`）。

**最终结论**：内核侧只做**联调取证**；**生产落点是用户态 compat 层**（原因见 `docs/01` §4）。

## ⑥ 照抄官方 `if (!fd[i]) continue;` ⇒ 静默漏掉输入缓冲

**症状**：输入缓冲从未被编程进 `ADDR*`；引擎取指正常但结果明显不对（或不动）。

**根因**：官方把"句柄 0"当空槽跳过，而**本库的输入缓冲句柄恰好就是 0**（page 0 = 150528 B 输入）。
额外坑：`all=7` 但实际只有 6 个有效槽（`idx[i]==0 && bufsizes[i]==0` 才是空槽）。

**修法**：空槽判据改为字段组合判断，不用 `!fd[i]`。

**顺带两个同源坑**：
- 官方 `phytium_npu_config_start_inference()` 里 `ctrl = min(2048, stream_size); ctrl = (ctrl/32 - 1) << 1;`
  **`stream_size == 0` 时在 u32 下溢成 `0xFFFFFFFF`**（引擎不取指、无报错）⇒
  桥接/兼容层**必须在 `stream_size == 0` 时直接拒绝并报错**，绝不能静默变成垃圾控制字。
- 官方 `phytium_npu_map_phys_range()` 一类"自建映射"函数曾**丢弃底层返回值并无条件 `return 0`**
  ⇒ 映射失败被静默吞掉、`e->mapped=1`、`CMD_BASE` 指向空页表。**凡自建映射一律检查返回值并落 err 日志。**

## 附：这些 bug 的共同教训

1. **"偶发 + 硬件计数完全相同" ⇒ 先审自己代码的未初始化/UB**，别从"硬件时序"起步；
2. **"小样本一直正常"是最危险的掩护**：尺寸白名单、句柄 0、单张图……都是"只在别的样本上才暴露"；
3. **判定与信号要给足可观测面**：每个新功能都"默认关 + 一路打印判定结果 + 一键回退"；
4. **不要用会被并发改变的量做完成判据**；
5. **推翻自己的结论时，立刻在文档里标注更正并指向新版**——否则下一个人会照着旧结论再跑一轮。
