# 11 · 排查方法论与工具（这几轮沉淀下来的"怎么查"）

> 本篇不讲结论，讲**怎么查**。项目里 60% 的时间花在"用一个便宜实验否掉一个贵猜想"，
> 而剩下的时间大多浪费在**方法错误**上。下面每一条都是真金白银换来的。

---

## 一、总原则

1. **每轮只做一件事**，留可复现证据（dmesg / 寄存器读数 / CRC / 反汇编）。
2. **把"结论"和"未验证假设"分开写** —— 我们曾两次把桥接自己的 bug 写成"硬件限制"。
3. **优先做"能一刀切开两种世界"的实验**，而不是并列罗列可能性。
4. **先排除回归**：动手改之前，先确认"上一次能跑"的状态还能跑。

---

## 二、★ 断言纪律：任何"编译→重载→验证"的循环都要断言构建成功

**踩过的坑**：脚本里"替换源码 → 编译 → `cp` 到 `/lib/modules` → 重载 → 跑验收"，
**编译失败时 `cp` 会静默地把上一次遗留的旧 `.ko` 又装一遍** ⇒
每次"验证"结果都一样，看上去"每档配置都通过/都失败"，**实际测的是同一个旧模块**。
我们因此白饶数小时，还发布了错误结论。

**必须断言三件事（缺一不可）**：

```bash
# ① 构建 0 error（捕获完整输出，不能只看最后一行——成功时它也会打印 Leaving directory）
make ... > /tmp/build.log 2>&1 || { grep -E "ERROR|error:" /tmp/build.log; exit 1; }
# ② .ko 确实重新生成
rm -f $T/mod.ko
make ... && [ -f $T/mod.ko ] || exit 1
# ③ 已加载模块指纹 == 磁盘
sudo cp -f $T/mod.ko /lib/modules/$(uname -r)/extra/
D=$(modinfo /lib/modules/$(uname -r)/extra/mod.ko | awk '/srcversion/{print $2}')
sudo insmod ... ; L=$(cat /sys/module/mod/srcversion)
[ "$D" = "$L" ] || exit 1
# ④ 参数表指纹（最能一眼看出装的是哪一版）
ls /sys/module/mod/parameters/
```

**高频构建失败原因**：把一个函数从 `static` 去掉给另一个文件用，却**忘了同步另一个文件**：

```
ERROR: "<symbol>" [<mod>.ko] undefined!
```

⇒ **换源码备份时要整组换（成对的 `.c` 一起），不要混搭**；`make clean` 后再编，避免陈旧 `.o`。

## 三、★ 取证纪律：跨运行比对必须先清日志缓冲

我们曾用"模型 A 的命令流与模型 B 的命令流逐字节相同"得出**"这段是公共前导块"的错误结论**，
成因是**第二次采集没有 `dmesg -C`**，文件里混进了第一次的内容 —— 比对到的是"自己的影子"。
清干净后重做，两条流**第一个字就不同**（`0x0400001a` vs `0x04000eff`）。

**判据**：比对前先确认两份数据里的**运行标识**（缓冲地址 / 页号 / 计数器）不同，否则就是自己的影子。

## 四、★ 回归排查：不要轻信"某个成绩不可复现"

我们曾拿"两个都晚于成功时刻的构建"做 A/B，然后宣称"老版本也不行 ⇒ 是既有问题"，
把一次**回归**误判成"从未成功"，白绕好几轮。

**正确做法**：
1. 找出"曾经跑对"的记录（交接件 / 报告 / 日志），取它写下的**输出数值与提交字段**
   （iova、idx、sz、CONTROL）—— 若与失败时**逐字段相同**，说明问题不在编程层；
2. **按时间戳找出当时刻的源码备份**，逐个回测：编译 → 重载 → 跑当时那个验收脚本；
3. 在"好的最后一档"与"坏的当前版"之间做**单因素回退**，一次只回退一行。

> **A/B 的"旧版"必须是成功时刻那一版。**

## 五、判据设计

| 判据 | 说明 |
|---|---|
| **写回判据**：缓冲 CRC 前后是否变化 | 驱动不做 memcpy 回写，所以这是"引擎到底写没写"的唯一硬判据 |
| **完成位不能单独当判据** | 坏配置照样能给 `done=1` 10/10，但 `cosine=0`。**必须同时看输出数值** |
| **访存计数 vs 命令流缓存行数** | `MMU_REQ_RD ≈ 命令流字节/128` ⇒ 引擎只把流取完了、没碰数据缓冲 |
| **同输入跑两遍** | 输入相同 ⇒ 结果相同 ⇒ CRC 恒定，"输出 CRC 变了"不能当完成判据 |
| **非法地址 canary** | 让引擎去访问非法地址：报页故障 ⇒ 引擎确实在取指（只用于判断"有没有动过"） |

### 反汇编定位法（找库的判定逻辑）

1. 先在库里找**错误字符串**的虚拟地址（`elf_va_strings.py`）；
2. 找**引用该字符串的代码位置**（`objdump -d` + 地址匹配）；
3. 往上追**调用者**与**分支条件**（我们就是这样定位到
   `GetVhaResponse` 取 `rsp+2` 的 u16、且只接受 1 或 4）。

## 七、驱动侧诊断码的使用纪律

- **诊断打印/转储一律"用完即删"**，并保留插入前的源码备份（`bakNN_xxx`）。
- 一次性诊断用**模块参数**开关（如 `vha_iova_mode` / `vha_boost_min`），
  这样一轮编译就能做 A/B，不用反复改代码。
- 收尾时核对**参数表指纹**，确认无实验参数残留。

## 八、症状 → 根因速查（累计）

| 症状 | 根因方向 |
|---|---|
| 数值对、但库报 `Error reading response` / 等待超时 | **响应里的 task-id 未回填**（`rsp->ursp +2` 须为 1 或 4） |
| 池路径 `-3 SERVER`，`nid = -1` | 同上 |
| `insufficient size of memory buffer (A < B)` | **EP 张量分配 vs 编译器 CNF 填充尺寸不一致**；`B` 来自编译器缓冲清单 |
| `Wrong command stream parser data` | 库解析网络二进制失败 —— 检查**回报给库的缓冲尺寸是否与请求一致** |
| 缓冲 CRC 前后一致、写回计数全 0、无任何错误标志 | **驱动写入/映射层**；先回测"曾能跑"的备份排除回归 |
| `stream_size == 0` 时引擎不取指且无报错 | `CONTROL` 编码在 u32 下溢成 `0xFFFFFFFF`（见 `docs/01` §1） |
| 同进程第二次推理慢 40 s | 看门狗把"循环次数"当"毫秒"（本内核 `msleep(1) ≈ 8 ms`） |
| 多模型挂死 | 厂商库按响应里的 `sid` 匹配任务，同进程内各图 `sid` 相同（见 `docs/04`） |
