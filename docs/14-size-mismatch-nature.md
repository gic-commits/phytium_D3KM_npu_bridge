# 14 · SenseVoice 卡点深挖：尺寸错位的性质判定（2026-10-02 深夜续）

> 承接 `docs/13`。本篇回答一个问题：**`457776 vs 913920` 到底是我们编译的问题，还是库内部的问题？**
>
> **结论：是库内部两套尺寸口径不一致，不是我们编译配置的问题。**
> 因此**"重编包"大概率不能解决它** —— 这条判断改变了后续方向。

---

## 一、先纠正一个我自己的判断

`docs/13` 里我把成因归到编译配置 `-mc in32out32_d16_w16b16.json`（"输入输出 32bit、数据 16bit" ⇒ 2 倍口径差）。
**深挖后这个归因站不住**，理由见下。

---

## 二、决定性事实：`913920` 不在任何编译产物里

在包里三处都搜不到这几个数（十进制与**小端十六进制**都搜过）：

| 搜索位置 | 913920 | 457776 | 228480 |
|---|---|---|---|
| `sensevoice.json` | 0 | 0 | 0 |
| `sensevoice.params`（二进制） | 0 | 0 | 0 |
| `npu_mbs.*`（挑最大的 35 MB 样本） | 0 | 0 | 0 |

⇒ **`913920` 不是编译产物里存的常量，而是库在运行时算出来的。**

而报错是"**库自己申请的** 457776 **小于** 库自己校验要的 913920" ⇒
**同一块缓冲，库有两套口径**（一套用于申请、一套用于校验）。

---

## 三、数字关系（精确）

```
228480 = 2^7 × 3 × 5 × 7 × 17
913920 = 228480 × 4.000000     ← 精确 4 倍
457776 = 228480 × 2.003571     ← ≈ 2 倍（不是精确 2 倍）
```

对照网络真实输入：

```
x[1,200,560] float32 = 448000
448000 / 228480 = 1.9608       ← 不是整数倍 ⇒ 228480 不是 x 的某个倍数
228480 / 4 = 57120 = 2^5 × 3 × 5 × 7 × 17
```

⇒ **`228480` 属于"另一组 shape"**（分解出 `17` 这个因子，`x` 的 560=2⁴×5×7 里没有它），
很可能是 FSMN 块里的某个中间张量。

---

## 四、旁证：当初的编译是"部分成功 + 手工修包"

`/data/usershare/AI编码项目/faster-whisper-NPU/` 下留有现场：

```
复盘(9-28):  "SenseVoice 编译（失败，工具链不支持算子）"
产物时间:    09-29 10:07（.json/.params/.so）、09-29 12:39（.tar）   ← 9-29 又编了一次
tarfix/      141 个 npu_mbs.*（1.1 GB）+ sensevoice_new.tar + new_names.txt
             ↑ 141 = 包里 npu_main 段数（141 个 NPU 段）
             ⇒ 当初把 141 个 mbs 单独拆出来重打包
```

三个版本的 `__internal_io_file__` 差异：

| 版本 | 大小 | 输出字段 |
|---|---|---|
| `bak_orig` | **0 字节**（空） | — |
| `bak_io` / `new` | 312 B | 无名 `[1,204,25055]` |
| **现用** | 207 B | **`logits`** `[1,204,25055]` |

⇒ 当初手工把"无名输出"补成了 `logits`（现用版是修好的）。
**但尺寸问题与 name 无关** —— 它来自库运行时的两套口径。

## 五、结论与方向修正

### 判断
1. **`457776 vs 913920` 是库内部尺寸口径不一致**，不是我们编译配置的问题
   ⇒ **重编包大概率不能解决它**（`docs/13` 的归因需要修正）。
2. 这与 `docs/10` 里 EP 侧的 `417792 vs 2445312`（也是编译器声明 vs 运行时分配不一致）
   **属同一类现象**：**厂商栈在"声明尺寸"与"实际分配尺寸"之间存在系统性不一致**。
3. 当初 SenseVoice 编译**部分成功**（141 段 MBS 编出来了），失败点在**打包/IO 口径**，
   而我们**已经手工修过一次**（`tarfix/`）—— 说明这条路上"手工修"是可行手段。

### 方向（按性价比）
1. **先试"修 IO 声明"而不是重编**：既然 `913920` 是运行时算的，试着让库申请时就按这个口径分配
   —— 即**在驱动侧对该缓冲按"校验口径"分配**（我们已有超配机制，此前用错了地方）。
2. 若 (1) 无效 ⇒ 说明是库内部逻辑，需**反汇编库的 IO 校验路径**（`is_input_node` / `has_segments_data`
   等符号都在），定位它为何用两套口径。
3. **重编包降级为备选**（且需要 2.7 GB 工具链镜像）。

## 六、方法记录

- **搜常量要同时搜十进制与小端十六进制**（二进制文件里存的是 LE）。
  本次三处都搜不到，才敢下"不是编译产物里的常量"这个结论。
- **数字关系要算到"精确/不精确"**：`913920/228480 = 4.000000`（精确）与
  `457776/228480 = 2.003571`（不精确）这个差别，直接指向"两套口径"而不是"简单倍数"。
- **遇到"部分成功"的历史产物，先找现场目录**（`tarfix/`、`*.bak_*`）——
  它们记录了前人（我们）当时怎么绕过去的，比重新推演快得多。
