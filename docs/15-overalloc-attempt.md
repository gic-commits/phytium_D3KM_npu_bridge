# 15 · 方向1 实测：按校验口径分配（机制可行，但受 CMA 总量约束）

> 承接 `docs/14`。本篇记录"让库按校验口径分配"这条路的**实测结果**。
>
> **结论：机制本身可行（能精确放大目标缓冲），但 SenseVoice 的 CMA 需求超出设备 1 GB 上限。**

---

## 一、做法（`HERMES-OVERALLOC` / `HERMES-OVERALLOC-EXACT`）

在 `VHA_ALLOC_MEM` 里把**"实际分配尺寸"与"回报给库的尺寸"解耦**：

```c
e->req_size = req.size;        /* 逻辑尺寸(库请求的) —— 回报给库 */
e->size     = vha_alloc_ask;   /* 实际分配尺寸(可放大) —— 内部用 */
```

两个模块参数控制：
- `vha_overalloc_mul`（默认 0=关）：按 N 倍放大（仅当 `req.size >= vha_overalloc_min`）；
- `vha_overalloc_exact`（默认 0=关）：**只放大"请求尺寸恰好等于该值"的那一块**。

**为什么要有 exact**：SenseVoice 全序列里 `x[1,200,560] f32 = 448000` **只出现 1 次**，
只放大它多花 0.46 MB；而全局放大不可行（见下）。

---

## 二、实测：机制生效

```
[VHA-OVERALLOC-EXACT] req=448000 -> ask=1347584 name=dnn_buf_
```

⇒ 精确匹配与放大都正常工作。

---

## 三、为什么全局放大不可行：CMA 预算不够

统计一次 SenseVoice 加载的**全部**分配（未放大）：

```
726 次分配，合计 364.3 MB
  417792 × 400 次 = 159 MB
  665856 × 322 次 = 204 MB
  （这两块占 99%；另有 448000×1、2240×2、4480×1）
```

尺寸序列**高度规律**（周期 9：`665856 665856 665856 417792 417792 665856 417792 417792 417792`），
**726 次分配、0 次释放** ⇒ 这是"**库为每个段都申请独立缓冲、段间不复用、也不释放**"，
**364 MB 是必需开销，不是泄漏**。

| 方案 | 需求 | 可用 CMA（基线 658 MB） | 结论 |
|---|---|---|---|
| 全局 2 倍 | ≈ 743 MB | 658 MB | ❌ 不够 |
| 全局 2.04 倍 | ≈ 743 MB | 658 MB | ❌ 不够 |
| **只放大 x（448000）** | 364 MB + 0.46 MB | 658 MB | ✅ 够 |

**精确倍数**（供参考）：
```
x[1,200,560] f32 真实 = 448000
库申请               = 457776 = 448000 × 1.0218
段 IO 校验要         = 913920 = 448000 × 2.0400   ← 精确 2.04 倍
                             = 457776 × 1.9964   ≈ 2 倍
```

## 四、⚠️ 实测中撞到的新问题：CMA 被"钉住"

只放大 x 那块的实验**没能跑完**，因为 CMA 已在此前的 2 倍放大实验中被吃到 4 MB：

```
CmaFree: 4048 kB
cma: cma_alloc: alloc failed, req-size: 329 pages, ret: -16   ← 连 1.3 MB 都分不出来
```

**而且这个状态清不掉**：
- `systemctl stop npusvc` + `pkill -9 npuworker` ⇒ 无效；
- `rmmod phytium_npu_platform` + `rmmod phytium_npu` ⇒ **CMA 仍是 4048 kB**；
- 无进程持有 `/dev/npu0`（`lsof` 空）。

⇒ **判断：CMA 分配器在压力下（1 GB 被占满）留下了未能回收的页**，
模块重载清不掉，**只能整机重启**。

> 这与 `docs/13` 里"373 MB 是环境基线（GPU/AI 运行时常驻）"是两回事：
> 那 373 MB 是**别人的**，这 1 GB 是**我们实验吃掉的**。

---

## 五、结论与下一步

### 结论
1. **"按校验口径分配"的机制可行**（`HERMES-OVERALLOC-EXACT` 已验证生效）；
2. **但 SenseVoice 的 CMA 需求（364 MB）加上基线占用，余量只有约 294 MB** ——
   任何"全局放大"都会失败，**只能做"精确放大"**；
3. **只放大 x 那块（+0.46 MB）在预算上是可行的**，但**本次因 CMA 已被吃干而未能验证**。

### 下一步（需要整机重启）
1. **重启**（回收 CMA）；
2. 用 `vha_overalloc_exact=448000`（3 倍 ⇒ 1347584 ≥ 913920）**重跑 SenseVoice**，
   看是否越过 `Buffer ID: 6 exceeds its capacity`；
3. 若越过 ⇒ 继续往下（可能还有别的段有同类校验）；
4. 若不过 ⇒ 说明校验的不止 x 一块，需**从库侧定位"哪些缓冲会被按什么口径校验"**
   （反汇编 `is_input_node` / `has_segments_data` 等符号）。

### 经验（写入方法记录）
- **CMA 是有限资源，实验前先算预算**：本次"全局 2 倍"直接吃干 1 GB，
  导致后续实验全部失败、且**只能重启恢复**。
- **放大要"精确到块"**：先用日志统计"哪些尺寸出现几次"，只放大目标块，
  而不是全局乘倍数。
- **`rmmod` 不能保证回收 CMA**：遇到"卸载后 CmaFree 不变"时，先看是不是被钉住，
  不要误判为"别人的占用"（对比 `docs/13` 那 373 MB 的情形）。
