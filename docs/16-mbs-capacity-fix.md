# 16 · MBS 容量字段修正：突破与教训（2026-10-03）

> 承接 `docs/14`（尺寸错位性质）与 `docs/15`（驱动侧放大尝试）。
> 本篇记录**从"驱动侧"转向"MBS 侧"**的过程与结果。
>
> **核心结论：`457776 vs 913920` 这类错位，是【编译产物 MBS 里的容量字段算错】，不是驱动问题，也不是库的运行时行为。**

## 二、决定性发现：两个数都在 MBS 里

**之前搜 `/opt/npu/model/` 找不到 `npu_mbs.*` —— 因为它们在 `sensevoice.tar` 里**（144 个文件）。

```
npu_mbs.oCCWLX:  0x2a8 = 457776 (type=3)   0x2e8 = 913920 (type=6)
npu_mbs.10PgI0:  0x358 = 418608 (type=3)   0x368 = 835584 (type=2)
```

**规律（量化）**：
```
容量 = 基准 × 2.0036（不精确）   ← 编译时算错
要求 = 基准 × 4.0000（精确）     ← 正确值

913920 = 228480 × 4.0000     457776 = 228480 × 2.0036
835584 = 208896 × 4.0000     418608 = 208896 × 2.0036
```

**⇒ 这是编译器的尺寸计算 bug**：容量字段用了错误乘数（`2.0036` 而非 `2.0`）。

## 三、⚠️ 关键教训：`tar -uf` 是追加，不是替换

**两次"改 MBS"实验其实都没生效**，因为：

```bash
tar -uf sensevoice.tar ./npu_mbs.oCCWLX     # ← 追加到末尾
tar -xf sensevoice.tar -O ./npu_mbs.oCCWLX  # ← 取【第一个】匹配项（旧的）
```

**证据**：
```
tar 里 oCCWLX 出现 2 次，总文件数 146（原 144 + 2）
tar 内 0x2a8 = 457776（旧值）   ← 库读的是这个
本地文件 0x2a8 = 913920（新值）
```

**⇒ 必须重建整个 tar**（解包 → 覆盖 → `tar -cf`），并**校验 tar 内的值**。

**⇒ 改了 MBS 里的这个字段，库报的值没变。**

## 五、strace 的新发现：库读的是 `__internal_io_file__.orig`

```
worker 打开的文件：
  ./__internal_io_file__.orig    ← 2 次 ★ 库读的是 .orig 版本！
  npu_mbs.zsxr9C / zqsQ9l / ...  ← 141 个 mbs 都读
```

**⇒ 当初手工修包时改的是 `__internal_io_file__`，但库读的是 `.orig`。**

**三个版本对比**：
```
tar 内 __internal_io_file__      (207B): x 有 name，输出无 name
tar 内 __internal_io_file__.orig (312B): x 有 name，输出无 name
tarfix/__internal_io_file__      (312B): 与 .orig 相同
```

**`x` 的 shape = `[1, 200, 560]` f32 = 448000** —— 不是 457776，也不是 913920。

## 七、经验（写入方法记录）

- **`tar -uf` 是追加，不是替换** —— 改 tar 内文件必须**重建**，且**校验 tar 内的值**（不能只看本地文件）。
- **搜二进制常量前先确认文件在哪** —— MBS 在 tar 里，不在 `/opt/npu/model/` 下。
- **strace 要抓对进程** —— 库在 `npuworker` 里读文件，不是 python 侧。
- **驱动侧改动前先确认"库读的是谁的值"** —— 本次三条驱动侧路线全否，根因是库用自己的记账。
