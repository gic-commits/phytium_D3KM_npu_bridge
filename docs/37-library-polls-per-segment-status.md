# 第八轮-30 ★库是"按段轮询状态"的；第 2 段状态=3 就是卡点

## 一、反汇编出的完整执行模型（已逐条验证）

`npu::VhaDnnImp::Execute` 的 lambda（0x1d3f8 起）：

```asm
1d3f8:  bl  VhaDnnTask::NextSegment()      ; 取"下一个段" → x20
1d404:  cbz x0, 1f394                      ; 取不到 → 跳出循环
1d408:  ldr x0, [x0]
1d410:  ldrh w0, [x0, #2]                  ; ★ 读**该段状态字段**的 u16
1d41c:  cmp w0,#0x4
1d420:  ccmp w0,#0x1,#0x4,ne               ; ★ 状态 ∈ {1,4} 才算"已完成"
1d424:  b.eq 1e008                         ; 已完成分支
1d428:  mov w0,#2 ; str [sp,#212]          ; 否则 status=2（未完成）
1d43c:  bl  VhaDnnTask::GetSubmitKey(w1)   ; 未完成 ⇒ 走"提交该段"路径
...
; 已完成分支 0x1e008：
1e018:  bl  VhaDnnTask::GetSlot()          ; 取本任务 slot
1e054:  mov w1, w23                        ; arg1 = slot
1e074:  bl  VhaObserver::HandleResponse(slot, cb, 0)   ; ← 等这条 slot 的响应
...
; 循环尾（段倒计数归零后）：
1dfa8:  subs w0,w0,#1 ; b.ne 1d3f8
1dfc0:  bl  VhaNotifyImp::Update(1)        ; 写状态（不 notify）
1dfcc:  bl  VhaDnnTask::Done::~Done()      ; ★ 触发 Signal ⇒ notify_all ⇒ 唤醒 WaitForCompletion
```

**⇒ 语义**：库**逐个段**检查其状态字段：
- 状态 ∈ {1,4} ⇒ 该段已完成 ⇒ 转去 `HandleResponse(slot)` **等这条响应**
- 否则 ⇒ 该段未完成 ⇒ 走 `GetSubmitKey` 路径**去提交该段**

## 二、★★★ gdb 实测到的段状态（决定性）

在 `0x1d414`（读完 `[x0+2]` 的下一句）断点，打印 `$w0`：

```
[09:21:00] 段状态#1 = 1   ★已完成
[09:21:00] 段状态#2 = 3   未完成      ← ★★★ 卡点就在这
[09:21:00] 段状态#3 = 1   ★已完成
[SUM] 读取次数=3 取值分布={1: 2, 3: 1}
```

**⇒ 第 2 段的段状态是 **3**，不属于 {1,4} ⇒ 库判定"该段未完成" ⇒ 进入提交路径 ⇒ 卡住。**
**⇒ 这就是"提交 3 次后停住"的直接机制。**

## 三、已排除：不是"响应条数不够"

推 96 条 / 254 条**同一键 `[+2]=1`** 的响应（`delay=50 + replay=30/80 + keep_slot=1`）：

```
提交=3  推送=96   库读=96    ⇒ 仍失败
提交=3  推送=254  库读=254   ⇒ 仍失败
```

**⇒ 库把 96/254 条全读走了，段状态仍然不变成 1/4 ⇒ 段状态**不是由响应队列设置的**。**

## 四·补 ★★★ 段状态字段的**归属已查明**：在库自己的堆结构里，不是驱动内存

用 gdb 在 `0x1d408`（`ldr x0,[x0]` 之前）打印段指针与内层对象：

```
#1 段指针=0x2b1390b0  inner=0x2b2095a0  inner[+2]=1
#2 段指针=0x2b223750  inner=0x2b223460  inner[+2]=3   ← 就是这个 3
#3 段指针=0x2b208330  inner=0x2b204eb0  inner[+2]=1
```

**而驱动侧我们的 IOVA 区间是 `0x48200000…` / `0x60xxxxxx…`，与 `0x2b2xxxxx` 完全不同**
⇒ **段状态字段位于库自己 malloc 的堆对象内，不是驱动映射的缓冲。**

**⇒ 因此：不是"驱动该往哪写"的问题，而是"库自己把这个字段置成了 3"。**
**⇒ 该字段的写入点在库内（全库仅 `VhaVaaHeapFree` 有一处 `strh [x,#2]`，与此无关 ⇒
   实际写入用的是别的指令形式：`strh` 带计算偏移、或 `str/stp` 覆盖更宽字段、或 `memset`）。**

**⇒ 下一步（精确、已在轨道上）：**
1. 在 `0x1d414` 处对 `inner` 设**内存写断点**（`watch *(unsigned short*)(inner+2)`），
   一跑就能抓到**是谁把它写成 3**（调用栈直接给出设置点）。
2. 抓到设置点后，看它的触发条件 ⇒ 就知道库在等什么。

**（这条路线的好处：`inner` 地址已能稳定抓到，watchpoint 是确定性的下一步。）**


**段状态字段的位置**：`NextSegment()` 返回段指针 → `ldr x0,[x0]`（段对象首成员）→ `[+2]`。
即状态存在**库为每个段维护的某个对象/缓冲**里，而该值**应由驱动或硬件在执行/完成时写入**（不是响应队列）。

**⇒ 下一步（精确）**：
1. 找出"谁写这个段状态字段"。它是 `VhaDnnTask::SetSegmentStatus` 之类，或**直接由驱动写入的映射内存**。
2. 观测到的取值 `1, 3, 1` 中，**3 很可能是"已提交/处理中"的中间态**；
   驱动需要把它推进到 **1 或 4**。
3. 检查我们的提交路径是否应向**某个每段的状态位**写入完成标记
   （可能是 CMDS 缓冲里的一段，或 MAP_BUF 出来的某个缓冲）。

**（这条线索比"响应键"精确得多：库的判定点、判定值、失败后果都已实测确认。）**

## 五、本轮其他确认
- 常量 `/` 序列键、`sid=slot`、常量 1/4 —— 全部无效（负结果）
- `vha_resp_fix=1` 会把响应 `[+2]` 强制改成 1 ⇒ **之前几轮"键序列"实验因此无效**（教训）
- 响应缓冲越界 8 字节已修（按厂商方式多分配）

## 六·补 进一步验证（两项，均偏负）

**(1) 对段状态字段设写断点 ⇒ 阻塞期间**零次写入**
```
[SETUP] ★已在 inner+2 (0x27b5a462) 挂写断点
[SUM] 段命中=5  状态写命中=0
```
⇒ 值 3 是在**更早的准备阶段**写好的；阻塞期间没有任何代码再改它。

**(2) 用 gdb 直接把段状态 `3 → 1`（模拟"本应发生的写入"）⇒ 仍未放行**
```
#1 段状态=1（已合规，不动）
#2 ★把段状态 3 -> 1 (inner=0xdfdc460)
[SUM] 段命中=2 强制修正=1   → 客户端仍 -3 SERVER
```
⇒ **段状态本身也不是最终卡点**（修正后库仍未前进）。

## 七、本轮结论（诚实的边界）

至此**驱动侧可控的变量已被穷尽**：
| 维度 | 结论 |
|---|---|
| 响应键（常量/序列/覆盖式/1 或 4） | 全部排除 |
| 响应条数（1 / 96 / 254 条） | 全部排除 |
| 响应结构/字段（与厂商逐字段对齐、补性能字段、修越界） | 已对齐 |
| 响应的 sid（提交值的 / slot 值） | 全部排除 |
| 段状态字段（库内部堆对象，非驱动内存） | 已定位；强制改为 1 也不放行 |
| 内存（CMA 碎片 ⇒ 建网失败） | ★ 已找到根因并修复（compact/drop_caches） |
| 完成判据（轮询猜 vs 中断） | ★ 已修复（IRQDONE），单段模型 6/6 全绿 |

**剩余卡点在库内部**：库在 3 次提交后停止推进，主线程阻塞于 `WaitForCompletion`，
而唤醒它的 `VhaDnnTask::Done::~Done() → Signal()` 只在**段倒计数归零**时被调用
⇒ 说明库认为"还有段没完成"，但其判定依据（段状态 3）既不是响应设置的，
也不是驱动内存 —— **需要更深入地逆向库的段状态机**（下一步：对 `inner` 结构整体设
`rwatch/awatch`，或在 `0x1f394`（段取完的出口）与 `0x1dfb8`（倒计数归零）各设断点，
看它究竟走到哪一条、以及 0x1f394 的触发条件）。
