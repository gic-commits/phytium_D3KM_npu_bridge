# 第八轮-33 ★★★★★★★ 卡点精确定位：库在第 3 次等待要 key=3，我们只推 key=1

## 一、决定性探针：`HandleResponse` 的**期望键**

`gdb_hrkey.py`（断 `VhaObserver::HandleResponse`（0x356c0）读 `x1`=slot/key；
断 `WaitForCompletion`；断 `Signal`），sensevoice 一次推理：

```
[44824.030]   Wait on notifier=0x368404e0
[44824.030] ★HandleResponse #1  x1(key)=1     ← ★ 期望键 = 1
[44824.030]   Signal notifier=0x368404e0      ← 被唤醒 ✓
[44824.050]   Wait on notifier=0x368e63b0     ← （无 HandleResponse ⇒ 走"提交"路径）
[44824.060]   Signal notifier=0x368e63b0      ← 被唤醒 ✓
[44826.910]   Wait on notifier=0x36916b20
[44826.910] ★HandleResponse #2  x1(key)=3     ← ★★ 期望键 = 3
[44852.670] （无 Signal）                      ← ★★★ 永远等不到
[SUM] HandleResponse=2  Wait=3  Signal=2
```

**⇒ 库的期望键序列是 **1, 3**（奇数递增）；我们的推送键**恒为 1**
   ⇒ 第 3 次等待要 3 却收不到 ⇒ 主线程永睡 ⇒ worker 超时击杀。**

**⇒ 这正是此前 `gdb_notifier.py` 测到的"5 个任务、5 次 Wait、4 次 Signal"里
   缺的那一次 Signal 的**直接原因**。**

## 二、为什么"奇数键序列"此前测过却无效 —— 两个原因

1. **`vha_resp_fix=1` 会把 `[+2]` 强制改成 1** ⇒ 早期所有"键序列"实验**实际交付的都是 1**
   ⇒ 实验无效（已在本轮确认须显式置 0）。
2. **键与提交不是 1:1**：本次实测里第 2 次等待**不是**"等响应"路径（无 `HandleResponse`），
   所以我们的第 2 次推送（key=3）被那一步消耗掉 ⇒ 轮到"要 key=3"的等待时，
   我们手上发的是 key=5 ⇒ **错位**。

**⇒ 因此正确策略不是"按提交递增"，而是**按库的等待序列排键**：**
   观测到的等待序列 = `[等1、提交、等3、…]` ⇒ 推送键应依次为 `1, (空), 3, …`

## 三、本轮测试结果（三种键配置，resp_fix=0）

| 配置 | mobilenet | sensevoice | 提交/推送 |
|---|---|---|---|
| `rsp_slot=1 step=2` | 2/2 ✓ | ✗ | 3/6 |
| `rsp_slot=1 step=1` | 2/2 ✓ | ✗ | 3/6 |
| `rsp_slot=2 step=2` | ✗ 连单段都崩 | ✗ | 2/4 |

⇒ **`step` 递增本身没错，但"按提交递增"与"库的等待序列"错位。**

## 四、下一步（精确规格已拿到）

**需要一份 `推送键 ↔ 等待键` 的对齐时间轴**：
1. 同时记录 `[VHA-PUSHRSP] slot=N`（驱动侧，带时间戳）与
   `HandleResponse x1=key`（库侧，带时间戳）→ 合并成一条时间轴。
2. 由此得出**该推的键序列**（例如 `1,?,3,?,5…`，其中 `?` 是被提交路径吃掉的位置）。
3. 用**白名单/序列参数**实现（新增 `vha_rsp_key_list`，形如 `"1,3,5,7"` 或"仅对等响应的推送计数递增"），
   而不再依赖"每次提交都递增"。

**⇒ 这是唯一能把 SenseVoice 打通的具体动作，且完全在驱动侧可控。**
