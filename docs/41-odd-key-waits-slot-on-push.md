# 第八轮-34 ★★★★★★★ 库登记的等待是奇数序列 1,3,5,7,9…；键对了管线就能推进一大截

## 一、决定性实测（这是全程最接近成功的一次）

配置：`vha_rsp_slot=-1  vha_rsp_slot_step=2  vha_slot_reset_on_sync=1  vha_resp_fix=0`

**⇒ 对比此前最好成绩：**
| 配置 | Wait | Signal | 结果 |
|---|---|---|---|
| `slot=1 step=0`（旧） | 5 | **4** | 卡死（第 5 个永不唤醒） |
| `slot=-1 step=2`（本次） | **9** | **8** | ★ 管线推进到第 9 个等待 |

**⇒ ⇒ 库会**连续登记奇数键 1,3,5,7,9…** 的等待；只要键序列对，管线就一直往下走。**

## 二、为什么还差最后一步：推送条数/起点对不上

驱动侧推送键（同一轮）：`slot=3, slot=5, slot=7 …`
**⇒ 库里等 1，我们推 3（差 2）⇒ 第一条不匹配；且推送条数少于等待条数。**

**⇒ 关键机制（已确认）：`vha_alloc_slot()` 会被**比实际推送多**的调用消费序号
（"幻影分配"，见第八轮29：计数起点 9 vs 基准 6），所以"起点参数"与"第一条真正推送的键"
之间有一固定偏移。**

| `rsp_slot` | 实际按键序列 | 说明 |
|---|---|---|
| `1` | 3, 5, 7 | 偏移 +2 |
| `-1` | 3, 5, 7 | 同上（该次） |
| `-3` | **4294967295**, 1, 3 | 首条被幻影分配吃成 -1 |
| `-5` | 4294967291, 4294967293 | 更偏 |

⇒ **要得到 `1,3,5`，需让"幻影分配"不消耗序号，或直接改成"按等待序"投递。**

## 三、下一步（唯一动作，方向已锁定）

**改代码：让 slot 序号只在"真正推送响应"时递增**（而不是在 `vha_alloc_slot()` 里递增）——
即在 `vha_push_response()` 成功入队时才 `n++`。这样：
- 第一次真正推送 = `vha_rsp_slot`（设为 1）
- 之后每次推送 +`step`（设为 2）⇒ 精确得到 `1,3,5,7,9…` = **库登记的等待序列**

**预期**：库的每个等待都能拿到对应键 ⇒ `Wait=Signal` ⇒ SenseVoice 打通。

**实现要点**：把 `atomic_inc_return(&vha_rsp_slot_seq)` 从 `vha_alloc_slot()` 移到
`vha_push_response()`（真实入队点），`vha_alloc_slot()` 只读不做自增。

## 四、本轮其他确认
- 按需投递（`rsp_on_read=1`，含 `ms` 变体）四种组合：全部无效
- 常量 `1` 能让 mobilenet 通、但让 sensevoice 卡在第 3 个等待
- `1,3,5` 序列会让 **mobilenet 失败**（它每次推理只需 `key=1`）⇒ **序列必须"每次推理复位"**
  —— 这也解释了为什么 `reset_on_sync=1`（每次推送前复位）与 `step>0` 不能同时用
- 已实测：`reset_on_sync=1 + step=2 + slot=1` ⇒ 键 3,5,7；`+ step=0` ⇒ 恒 1

## 五、★ 已实现并验证：序号只在真正推送时递增（HERMES-SLOTONPUSH）

**实现了**：`vha_alloc_slot()` 在 `vha_slot_on_push=1` 时不再自增（返回 0 占位），
`vha_push_response_now()` 在**入队时**才 `atomic_inc_return()` 计算真实键。构建通过，
新参数 `/sys/module/phytium_npu/parameters/vha_slot_on_push` 已存在。

**验证**：`vha_slot_on_push=1 + vha_rsp_slot=-1 + vha_rsp_slot_step=2 + slot_reset_on_sync=1`
⇒ 实际推送键 = **1, 3, 5**（与库登记的等待序列**完全一致**）。

**结果：sensevoice 仍然失败；且 mobilenet 也失败（0/3）。**

## 六、★ 结论修正（诚实记录）：键序列不是最终答案

| 假设 | 验证 | 结果 |
|---|---|---|
| 库登记 1,3,5,7,9 ⇒ 只要交付同序列即可 | 已精确交付 `1,3,5` | ✗ **仍失败** |
| 常量键 1 可行（mobilenet） | 6/6 通过 | ✓ 但 sensevoice 卡第 3 个等待 |

**⇒ 库 `HandleResponse(key)` 里的 key 是**它内部的段/task 标识**，
   不是"驱动必须回填的响应键"——交付同值并不能完成那个等待。**

**⇒ 因此"响应键"这条线（第八轮 27~34 共 8 篇）到此**穷尽**：
   - 常量 / 递增 / 覆盖式 / 奇数序列 / 按需投递 / 只在真实推送时递增 —— 全部实测，全部无效。

## 七、真正剩余的卡点（收敛后的唯一结论）

**库在多段路径下：`Wait=9`、`Signal=8` —— 最后一个等待永远等不到 `Signal`。**
而 `Signal` 由 **同一个 task 的完成**触发 ⇒ **有 1 个段的任务永远没完成**。
库为此登记的等待（`HandleResponse(key=奇数)`）**不是靠驱动回填响应能满足的**，
而是靠**该段真的被 NPU 执行完**。

**⇒ 下一步唯一方向（驱动侧）：让"最后一次提交"真的发生并被硬件执行完。**
   - 观测：`提交=3`（而 `Wait=9`）⇒ **库登记的等待数 ≫ 实际提交数** ⇒
     有些段库**没有提交**（因为它认为"已完成"，见第八轮30 的段状态轮询）
     ⇒ 那些段永远不会有完成中断 ⇒ 对应的等待永不被唤醒。
   - 即：**要修的是"段状态"的判据**（让库认为这些段**未完成**、从而去提交它们），
     而不是响应键。
   - 段状态字段在库堆对象内（第八轮30/31 已定位）；**它由库自己写**，
     但判据可能与我们提交的"描述符/流"内容有关（例如流里必须带某标志）。
     ⇒ 回到**提交内容**（T1'/CMDS/MBS 那条线）去查：库凭什么把某段标成"已完成"。
