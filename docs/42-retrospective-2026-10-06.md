## 二、已经定案、且**至今未被推翻**的结论（★ = 关键）

### ★ 2026-09-27 · 第三十轮：库的"响应→任务"匹配缺陷
> 库只用 **`npu_user_rsp.sid`** 判断"响应属于哪个任务"；而**同一进程内不同图的提交 sid 恒为 `0x10101`**
> ⇒ 第 2 条响应被投递给第 1 个图留下的任务对象 ⇒ 新任务永收不到完成 ⇒ `WaitForCompletion` 永久阻塞。
> **处置**：单引擎模式 / 每模型一进程（**已实测通过**：5 模型轮换、并发、超时击杀、systemd 六项验收全过）。

**⇒ 这条直接适用于今天：SenseVoice 是**单图内 5 个任务**，sid 同样全是 `0x10101` ⇒ 同一缺陷在单图内复现。**

### ★ 第八轮 13/14：阻塞点与判据
- 阻塞点 = `VhaNotifyImp::WaitForCompletion`（`libphydnn_execute.so → npu_phydnnWaitForEvent`）
- `WaitForCompletion` 等的是 **`this+256`（status）变为非 0**；`Update(status)` 写 `this+256`
- `HandleResponse` 之后确实找到节点且队列非空（"响应投递"上游已通）

### ★★ 第八轮 15：**库处在"重试/重放循环"里**（今天完全没提，但很关键）
```
[W20] 段数 = 8   [W20] 段数 = 1   [UPD] Update(status=1) 第 1 次
[W20] 段数 = 8   [W20] 段数 = 1   [UPD] Update(status=1) 第 2 次   …（循环 7 次）
```
⇒ **每任务段数 = 8；完成置位被**反复触发**；W20 呈 `8,1,8,1…` ⇒ 库在**重试循环**中**，
更接近"执行跑完了但结果不被接受 ⇒ 重试 ⇒ 30s 超时"，**而不是单纯死等**。

### ★★★★ 第八轮 19：**第 2 次提交后硬件不执行**（最锋利，今天未提）
对照 mobilenet 连跑两次（提交参数**逐字节完全相同**）：
| | 第 1 次 | 第 2 次 |
|---|---|---|
| 结果 | 成功 | **失败** |
| `[VHA-SUBMIT] done=` | `done=1 after 7~11ms` | **`done=0 after 5003ms`** |
| `EVENT_STATUS` | 有事件 | **`0x0`** |
| `VHA-CRC-after` | 变化 | **与 before 完全相同（输出没被写）** |
| **唯一差别** | — | **`NPU_CH0_STATUS=0x1` + `NPU_CH0_CONTROL=0x307e`（上一轮残留）** |

⇒ **NPU 核的残留状态导致下一次提交不被执行。**

### ★ 第八轮 16：多段才是卡点 + 库内部尺寸口径不一致
- 驱动对**单段模型完全正确**（mobilenet/Restnet50/ppocrv3_cls 均通）
- 多段包（sensevoice 141 段 / sv0 37 段）卡死
- svtest 有**明确报错**：`Buffer ID: 6 exceeds its capacity. size 457776, but segment IO declares 913920`
  ⇒ `913920 = 228480×4`；两个数**运行时算出来的**，json 里搜不到
- **我们改 MBS `0x368` 声明尺寸绕过了该检查 ⇒ 把"显式报错"变成"静默挂死"**

### ★ 第八轮 17 / 28：CMA 两轮定案
- 17：CMA 分配路径上的内核死锁（`cma_alloc → drain_all_pages → flush_work`）
- 28：**CMA 碎片化**导致 30MB `TMP-13` 建网失败（`ret: -16`，容量充足）⇒ `drop_caches + compact_memory` 可解

### ★ 第八轮-lost-wakeup根因：同步推响应导致丢失唤醒
> 厂商是**异步**完成（IRQ 后推响应）⇒ 响应必然晚于 `wait()`；
> **我们的驱动在 submit ioctl 内部同步推响应** ⇒ 响应早于 `wait()` 入队并被消费并 notify ⇒ 丢失唤醒。

### ★ 第八轮 24：完成判据改用中断（重大修复）
轮询猜完成（库消费响应/CRC 变化）⇒ 失败时 `done=0` 不推响应 ⇒ 挂死；
改用 **`NPU_INFERENCE_COMPLETE` 中断计数**后单段模型 6/6、4/4 全绿。**此修复有效至今。**

## 四、今天（第八轮 25~34）真正的新知（去重后剩下的）

1. **响应键的真实语义**：库登记 `HandleResponse(key=1,3,5,7,9…)`；`[+2]` 是 map key。
   用 `slot=-1 step=2` 把键调对后，**`Wait=9 / Signal=8`**（此前 `5/4` 卡死）⇒ 管线推进一大截。
2. **`vha_resp_fix=1` 会把 `[+2]` 强制改成 1** ⇒ **早前所有"键序列"实验因此无效**（方法论坑）。
3. **`vha_alloc_slot()` 存在"幻影分配"**（分配数 > 实际推送数）⇒ 键整体偏移；已实现
   `HERMES-SLOTONPUSH`（序号只在真正入队时递增），可精确产出 `1,3,5`。
4. **库的 5 个任务在 `load` 阶段由 `VhaDnnImp::InitResources` 创建**（`observer=NULL`）。
5. **两模型的 ioctl 特征完全不同**：mobilenet 有 `nr=9(BUF_OP)/nr=10(OUTPUT_SYNC)/提交`；
   **sensevoice 只有 `nr=0/nr=2/nr=7` ⇒ 从未进入提交/编程阶段，零提交、零完成中断。**

## 五、统一因果链（把 9/27 与 10/5-10/6 的结论接起来）

```
[1] 库只用响应 sid 匹配任务，而 sid 恒为 0x10101（9/27 定案）
      ↓ 单段模型：任务对象复用 ⇒ 不冲突 ⇒ 能通
      ↓ 多段模型：单图内 5 个任务同 sid ⇒ 响应无法区分 ⇒ 唤醒错配
[2] 叠加：我们的驱动在 submit ioctl 内**同步**推响应 ⇒ 丢失唤醒（10/05 定案）
[3] 叠加：NPU 核残留状态 NPU_CH0_STATUS=0x1 ⇒ 第 2 次提交不被执行（第八轮 19）
[4] 叠加：多段包的库内部尺寸口径不一致（913920 vs 457776），被我们用改 MBS 绕过
      ⇒ 由"显式报错"退化为"静默挂死"
[5] 现象层：库进入 8,1,8,1 重试循环（第八轮 15）；Wait 多于 Signal
```

## 八、★★★★★★★ 回溯的**最重要发现**：这条路的答案早就有了（NAS 独有文档）

NAS 上有 25 篇本机没有的文档，其中两篇**直接否定我们这些天做的路线**：

### ★★★ 8.1 `给麒麟智能体-运行时段数限制-2026-09-29.md`（2026-09-29 已定案）
> 1. 设备现装的 PHYDNN 运行时（libphydnn 2026-02-05 / libphyaiengine 2025-12-16）**只支持【单段】模型**
> 2. 多段包（tar 里 >1 个 `npu_mbs.*`）会在**执行时创建网络**阶段失败：
>    `Buffer ID: 6 exceeds its capacity ... segment IO declares size: 913920` ⇒ `unable to create network`
> 3. 因此：**不要把多段大模型部署到 `/opt/npu/model/` 试跑**（白费时间，还可能让 worker 崩溃）

**⇒ 我们昨天看到的 `913920 vs 457776` 正是这条；而我们"改 MBS 绕过"⇒
  把一个**明确报错**退化成**静默挂死**（第八轮16 也写过这句，但被后面的轮次忽略了）。**

### ★★★ 8.2 `给智能体-SenseVoice上飞腾NPU两个方向-2026-10-01.md`（2026-10-01 已给答案）
> - 官方规格：该 NPU **仅面向 CNN**，"不支持 Transformer/LLM 类模型"
> - 路径 A（多段包 37/141 段）→ 运行时报 `913920` 容量错
> - 路径 B（清成单段 seg=1）→ mapper 失败于 `Format mismatch … exponent:-12 vs -11`（transpose + batch_matmul）
> - **★ 追加（16:20）：官方正路 = 定制 ONNXRuntime 异构推理**
>   EP = `PHYNPUExecutionProvider` + `CPUExecutionProvider` 并用；`unspported_nodes_file` 把不支持节点交 CPU
> - **结论：SenseVoice 走厂商离线 MBS 流水线**不可行**；走【定制 ONNXRuntime】**可跑**。**
